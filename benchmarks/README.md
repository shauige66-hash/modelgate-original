# 基准测试

在**真实 PostgreSQL** 上对 ModelGate 做可复现的压测，上游是可控延迟与故障率的 Mock 服务，
不消耗任何真实模型额度，也不写入业务库。

## 结论先行

主脚本：`acceptance.py`。同一批次内跑完所有场景，负载生成器跨轮次复用同一连接池，
每个场景每档并发重复 3 次并记录**每一轮**的结果。

实测（Mock 上游注入 30ms，每档 1000 请求 × 3 轮 = 3000 请求，全部成功）：

| 场景 | 并发 | 中位 RPS | 各轮 RPS | p50 | p99 | 错误率 | PG 连接峰值 |
|---|---|---|---|---|---|---|---|
| 配额关 | 10 | 66.3 | 60.1 / 66.3 / 69.6 | 162 ms | 239 ms | 0% | 11 |
| 配额关 | 20 | 63.0 | 61.8 / 63.0 / 66.0 | 316 ms | 457 ms | 0% | 15 |
| 配额关 | 50 | 64.1 | 62.7 / 64.1 / 65.5 | 739 ms | 1054 ms | 0% | 29 |
| 配额开 | 10 | 50.7 | 49.9 / 50.7 / 53.0 | 187 ms | 270 ms | 0% | 11 |
| 配额开 | 20 | 43.9 | 41.4 / 43.9 / 50.1 | 453 ms | 1062 ms | 0% | 20 |
| 配额开 | 50 | 48.4 | 44.3 / 48.4 / 49.5 | 712 ms | 3680 ms | 0% | 31 |

**配额开关对比**：c=10 时 −23.5%，c=20 时 −30.3%，c=50 时 −24.5%。
**配额带来的 p99 代价在 c=50 时最明显：从 1,054 ms 升到 3,680 ms。**

### 分项归因

| 环节 | 吞吐 | 说明 |
|---|---|---|
| Mock 上游直连 | 253–296 RPS | 压测工具与 Mock 自身的上限 |
| 网关鉴权拒绝（不碰 DB、不打上游） | ~250 RPS | 网关纯转发路径的上限 |
| 网关完整链路（写一条调用记录） | 63–66 RPS | **写入 PostgreSQL 是主要开销** |
| 网关完整链路 + 配额预扣 | 44–51 RPS | 再叠加一个短事务与一次额外连接取用 |

三点值得注意：

1. **吞吐在 c=10 就已饱和**（66 RPS），c=20/50 不再提升，只是延迟线性上升。
   说明瓶颈是某个串行化环节，不是并发度不足。
2. **配额开销基本是固定值**（约 −16 RPS），在三种并发下比例接近，
   符合「每请求多一次短事务」的定性。代价主要体现在 p99。
3. 全部 18000 次请求 **0 错误**，且每档 3000 次全部落库。

### 这些数字不能用来宣称什么

- **不能宣称生产容量。** 全部数据来自单机 Mock 环境，压测客户端、网关、
  Mock 上游与 PostgreSQL 同机运行，互相争抢 CPU。
  汇报时必须同时给出环境，否则数字没有意义。
- **不能宣称真实模型服务的表现。** Mock 上游固定 30ms，真实推理通常数百毫秒到数十秒。
  本基准测的是**网关自身处理与持久化开销**。
- **不能宣称优化收益。** 本轮没有做任何针对性优化，也没有可对照的优化前后数据。
- **不能把 c=10/20/50 的 RPS 差异解释为扩展性结论。** 三者吞吐接近，
  只能说明当前配置下 c=10 已触到瓶颈，不能推断更高并发的行为。

## 关于 c=50 的 502：根因排查结论

第一轮基准曾在 c=50 观察到 5.8%–14.4% 的 502，当时我判断是「连接池反压」。
本轮做了证据化排查，**这个判断是错的**，在此更正。

### 已经排除的假设（有直接证据）

| 假设 | 证据 | 结论 |
|---|---|---|
| Mock 上游返回 502 | 上游侧日志 5586 次请求**全部 200** | 排除 |
| PostgreSQL 连接耗尽 | 连接峰值 31，`max_connections=100` | 排除 |
| 配额行锁争用 | `pg_stat_activity` 锁等待计数恒为 0 | 排除 |
| SQLAlchemy 连接池耗尽 | 未出现 `QueuePool` / `TimeoutError` | 排除 |
| 上游到网关的连接池耗尽 | 未出现 `httpx.PoolTimeout`（那会是 504） | 排除 |
| 端口耗尽的硬上限 | 干净批次 18,000 次请求 0 错误 | 排除为**必然**原因 |

### 尚未完全证实、但指向明确的证据

| 观测 | 数值 | 说明 |
|---|---|---|
| Windows IPv4 动态端口范围 | 49152–65535，共 **16,384** 个 | `netsh int ipv4 show dynamicport tcp` |
| 高负载时实测 TIME_WAIT | 峰值 **23,801** | 已超出动态端口总数，说明计数含 IPv6 与其他进程 |
| 空闲时 TIME_WAIT | 678（其中 654 属内核 Idle） | 说明 TIME_WAIT 主要集中在压测期间产生 |
| 失败样本分层 | 约八成是**无 body、无 Server 头的裸 502** | 不是 ModelGate 生成的响应 |
| 压测客户端侧 | 大量 `ConnectError: All connection attempts failed` | 连网关都没连上 |
| 网关侧 | 混合出现 `upstream_connect_error` 与 `upstream_http_error` | 到上游建连也失败 |

失败与机器负载强相关：并发跑其他工作负载时出现，机器空闲时连续 8000 次请求全绿。

### 措辞与置信度

**高度怀疑**由同机压测环境与连接资源竞争引起 —— 负载生成器、网关、Mock 上游、
PostgreSQL 与 Docker 全部跑在同一台同时运行 IDE / 浏览器 / 代理的机器上，
高并发下临时端口与 SYN backlog 承压，表现为环回连接被拒。
**这尚需在独立环境验证，本轮不能断言为已证实的唯一根因。**

未闭合的证据缺口：

1. 裸 502 的具体产生者未定位。它没有 ModelGate 的错误响应格式，
   也不是 Mock 上游返回的（上游只返回 200/429/500），但也没有抓到
   产生它的进程级证据（如 WFP/代理拦截或 TCP 栈行为）。
2. 没有在失败瞬间同步采样端口耗尽计数，因此「端口压力」与「失败」
   是相关而非因果已证。
3. 缺少独立环境（压测机与被测机分离）的对照实验。

### 因此本轮的最小修改

**没有修改 ModelGate 的超时或连接池参数。** 没有证据支持这类改动，
调大参数只会把问题藏起来（这也是要求里明确禁止的做法）。

做的改动都在**测量侧**，让下次不再误判：

- `load.py` 记录失败样本的**分层信息**（客户端异常类型 / 网关 error.type / 原始响应头）
- `load.py` 区分「网关生成的 JSON 错误」与「无 body 的裸错误」
- `acceptance.py` 复用单一连接池，并采样 `pg_stat_activity` 排除数据库因素
- `probe_connection_scope.py` 用连接池事件证明请求期间是否持有连接

### 残余风险

- 本机饱和时 502 会复现。**上线前必须在独立环境重测**，否则无法区分
  「网关容量不足」与「压测机自身过载」。
- 生产环境若网关与上游或数据库跨网络部署，环网饱和问题不存在，
  但会出现真实的网络超时，那时才需要按实测数据调整超时与重试。

## PostgreSQL 开销与事务边界

用 SQLAlchemy 连接池事件观测一次请求的连接持有时间（`probe_connection_scope.py`）：

```
预扣完成      t=  119.9 ms
上游调用完成  t=  425.2 ms   (模拟上游占 300ms)
记录落库完成  t=  449.7 ms

连接池事件：
  checkout  t=  100.9 ms
  checkin   t=  119.6 ms     <- 配额预扣，持有 18.7 ms 后归还
  checkout  t=  426.0 ms
  checkin   t=  449.5 ms     <- 调用记录写入，持有 23.5 ms

与上游调用重叠的连接持有区间：无
```

**结论**：配额预扣在独立短事务中提交后立即归还连接，
上游调用期间**没有任何数据库连接被持有**。
这正是预扣设计要保证的性质 —— 行锁不跨上游请求持有。

配额开启后的额外成本是一次短事务：多一次连接取用、一次 UPSERT、一次 COMMIT。

### 这段观测的限制（不要过度解读）

- **是单次观测，不是分布。** `18.7 ms` / `23.5 ms`（另一次运行 19.0 ms / 32.1 ms）
  只是各一次采样，**不代表所有请求的持有时间**。要谈分布需要打点统计，
  本轮的连接池事件观测只用于证明「请求期间是否持有连接」这一结构性事实。
- **条件与主基准不同。** 该观测里上游等待用 `asyncio.sleep(0.30)` 模拟 300ms 推理，
  而主基准的 Mock 上游固定 30ms。**两者不可直接比较**：
  观测脚本的 300ms 是为了模拟更接近真实 LLM 的耗时，以检验「长上游等待期间是否持有连接」；
  基准的 30ms 是为了让网关自身开销在端到端延迟中占比可辨。
- **首连接含建连成本。** 观测脚本每次新建引擎，第一次 checkout 含 asyncpg 建连，
  因此绝对值偏大；预热后的稳态值会更低。

### 可以优化的点（本轮未做，因为缺少同条件证据）

`upstream.py` 的 httpx 客户端未显式设置 `max_connections`，用的是 httpx 默认值 100。
当网关内部并发上限高于该值时，请求会在**网关到上游**的池里排队，
表现为 `PoolTimeout`（504）而非 502。当前默认配置
（`MAX_CONCURRENT_REQUESTS=8`、`UPSTREAM_MAX_CONNECTIONS=100`）不会触发，
但把并发上限调高时需要注意两者匹配。这是一条**基于配置关系推理**的提示，
不是本轮的实测结论。

## 运行方式

```powershell
# 专用测试库（库名必须以 _test 结尾，脚本会拒绝其他库）
docker compose exec db psql -U modelgate -d postgres -c "CREATE DATABASE modelgate_test;"

$env:TEST_DATABASE_URL="postgresql+asyncpg://modelgate:modelgate@127.0.0.1:5432/modelgate_test"

# 主基准：同一批次内完成配额开关对照，每档 3 轮
python -m benchmarks.acceptance --requests 1000 --concurrency 10 20 50 --repeats 3 --label acceptance

# 连接持有时间观测
$env:DATABASE_URL=$env:TEST_DATABASE_URL
python -m benchmarks.probe_connection_scope

# 四层分段诊断（Mock 直连 / 鉴权拒绝 / 完整链路）
python -m benchmarks.diagnose
```

输出：控制台汇总 + `benchmarks/results/<label>-<UTC时间戳>.json`。

## 指标口径

- **延迟**：端到端，客户端发出到收到响应，**包含** Mock 注入的 30ms。
  `gateway_overhead_ms` 是减去注入延迟的近似值，仍含本机网络往返。
- **RPS**：总请求数 / 墙钟时间。同一批次内重复 3 次，报告给出每一轮而非只有平均。
- **错误率**：非 200 响应 + 客户端异常的占比。
- **落库完整率**：由 `run_benchmark.py` 记录为「落库记录数 / 上游收到请求数」，应 ≥ 1
  （每条到达上游的请求都要留痕；未连上上游的失败调用同样要留痕）。

## 测试环境

| 项 | 值 |
|---|---|
| OS | Windows 10.0.26200 |
| CPU | 16 逻辑核心 |
| 物理内存 | 15.8 GB |
| Docker Engine | 29.8.2（linux 容器） |
| PostgreSQL | 16，`max_connections=100`，`shared_buffers=128MB`，语句日志关闭 |
| 容器资源限制 | 无（`Memory=0`，`NanoCpus=0`） |
| 网关进程 | 单个 uvicorn，`MAX_CONCURRENT_REQUESTS=64`，`DB_POOL_SIZE=10`+`20` |
| Mock 上游延迟 | 固定 30 ms |

**这些数字不代表 DeepSeek / OpenAI 等真实服务的表现。** 真实模型推理延迟通常在
数百毫秒到数十秒，远高于此处的 30ms Mock，因此本基准测的是**网关自身处理与持久化开销**。

## 文件说明

| 文件 | 作用 |
|---|---|
| `acceptance.py` | **主脚本**：同批次配额开关对照，复用连接池，记录每轮明细与 PG 峰值 |
| `probe_connection_scope.py` | 用连接池事件观测请求期间是否持有数据库连接 |
| `diagnose.py` | 四层分段诊断，定位瓶颈在哪一层 |
| `run_benchmark.py` | 早期版本：含落库完整率与故障注入参数，仍可用于注入场景 |
| `mock_provider.py` | 可控延迟与故障率的 Mock 上游（`--access-log` 可逐请求记录） |
| `load.py` | 并发压测与百分位计算，含失败分层采样 |
| `results/*.json` | 原始结果，含环境快照与每轮明细 |
